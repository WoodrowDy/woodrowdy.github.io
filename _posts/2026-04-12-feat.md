# LLM 위키(LLM Wiki)로 지식을 복리로 쌓는 법

## TL;DR

안드레 카파시(Andrej Karpathy)가 공개한 LLM 기반 나무위키 시스템은 개인의 노하우·자료를 AI가 자동으로 위키 페이지로 정리하고 교차 참조까지 생성해주는 지식 관리 시스템이다. Obsidian + Claude Code 조합으로 구현 가능하며, 로컬 파일(마크다운) 기반이라 가볍고 프라이버시가 보장된다. RAG처럼 단순히 문서를 검색하는 것이 아니라 **지식이 복리로 쌓이는** 구조가 핵심이다. 소규모 팀이 컨텍스트를 AI에게 주입하고 "나에게 맞춤형" 답변을 받고 싶을 때 매우 유용하다.

---

## 영상이 다룬 핵심 개념

### 1. LLM 위키의 3층 구조 [01:47]
- **1층(Raw 데이터)**: 기사, PDF, 회의록, 메모 등 원본 자료를 저장하는 폴더
- **2층(Wiki 페이지)**: AI가 원본을 읽고 나무위키 스타일의 페이지를 생성하며 교차 참조(cross-reference) 링크도 자동 삽입
- **3층(스키마/규칙)**: `claude.md`에 시스템 프로세스(로우 데이터를 어떻게 위키로 만들 것인지)를 정의

### 2. 기존 시스템과의 차별점 [04:54]
- **노트북 LM**: 구글의 RAG 기반 서비스. 자료를 올리면 똑똑하게 답변하지만 "지식이 복리로 쌓인다"고 보기는 어려움
- **RAG 시스템**: 벡터 DB에 임베딩을 저장해 유사도 기반 검색. 대용량 문서 검색에 강하지만 인프라 비용 발생, 설정 복잡도 높음
- **LLM 위키**: 새 자료가 추가되면 기존 페이지를 업데이트하거나 새 페이지를 생성. 교차 참조가 자동으로 증가하며 지식이 **복리처럼** 성장

### 3. Obsidian의 역할 [04:30]
- LLM 위키의 **뷰어(Viewer)** 역할
- 로컬 마크다운 파일을 그래프 형태로 시각화 (Command+G / Ctrl+G로 그래프 뷰 열기)
- 웹 클리퍼 확장으로 기사·블로그를 한 번에 `raw/` 폴더에 추가 가능

### 4. Claude Code의 역할 [04:33]
- 로우 데이터를 읽어 위키 페이지를 생성하는 **편집자(Editor)**
- 교차 참조 링크, 인덱스 업데이트, 로그 기록을 모두 자동화
- 10분 주기 루프(Loop) 실행으로 새 자료 10개씩 자동 반영 가능 [18:41]

### 5. 건강 검진(Lint) 모드 [03:23]
- 시간이 지나면 지식이 모순되거나 노후화될 수 있음
- Claude Code에게 "위키 건강 검진 해줘" 요청 시, 인덱스 정합성·교차 참조 누락·갭(Gap) 분석 후 개선 작업 수행 [24:14]

## 이론적 배경

### 1. 지식 그래프(Knowledge Graph)와 연결주의(Connectionism)
- 이 시스템은 전통적인 지식 그래프(노드=개념, 엣지=관계)를 LLM이 자동 생성하는 방식이다.
- **제텔카스텐(Zettelkasten)** 같은 노트 테이킹 방법론과 유사하지만, 인간이 수동으로 링크를 거는 대신 LLM이 자동 교차 참조를 수행한다.

### 2. RAG(Retrieval-Augmented Generation) 대비 차이
- RAG는 **검색(retrieval) + 생성(generation)** 파이프라인: 질문이 들어오면 벡터 유사도 기반으로 관련 청크를 찾아 LLM에게 전달
- LLM 위키는 **사전 정리(pre-organization)** 방식: 자료가 들어올 때마다 위키 페이지로 소화(digest)하므로, 질문 시점에는 이미 정리된 페이지를 참조
- 비유: RAG는 "도서관에서 책 찾아주기", LLM 위키는 "사전에 백과사전 항목 작성"

### 3. 멀티 에이전트 오케스트레이션 관점
- 영상에서 명시되지 않았지만, 이 시스템은 "단일 에이전트가 여러 역할(페이지 생성, 교차 참조, 린트)을 순차 수행"하는 워크플로우로 볼 수 있다.
- 향후 확장 시, 생성 에이전트와 검증 에이전트를 분리하는 멀티 에이전트 패턴 적용 가능 (예: LangGraph의 StateGraph, AutoGen의 ConversableAgent)

## 기존 솔루션 / 라이브러리와의 비교

| 항목 | LLM Wiki (Obsidian + Claude Code) | 노트북 LM | RAG (Pinecone/Qdrant + LangChain) | Obsidian (수동) |
|------|-----------------------------------|-----------|----------------------------------|----------------|
| **복리 축적** | ⭐⭐⭐ (새 자료가 기존 페이지 보강) | ⭐ (독립 문서로만 존재) | ⭐⭐ (임베딩 업데이트는 가능하나 지식 연결은 별도 구현 필요) | ⭐⭐⭐ (수동이면 가능, 자동화 없음) |
| **인프라 비용** | 낮음 (로컬 파일 + API 호출) | 무료 (구글 제공) | 높음 (벡터 DB 비용) | 무료 (로컬 전용) |
| **설정 복잡도** | 낮음 (Obsidian + VS Code) | 낮음 (웹 UI) | 높음 (임베딩 모델, 벡터 DB, 청킹 전략 등) | 중간 (플러그인 설정) |
| **대용량 문서** | ⚠️ 수백 페이지까지 (수만 개는 비효율) | ⚠️ 소스당 50개 제한 | ⭐⭐⭐ (수십만 건 가능) | ⚠️ 로컬 파일 한계 |
| **교차 참조 자동화** | ⭐⭐⭐ (LLM이 자동) | ❌ | ❌ (메타데이터 별도 관리 시 가능) | ❌ (수동) |
| **프라이버시** | ⭐⭐⭐ (로컬 파일 + API만 외부) | ⚠️ (구글 서버) | ⚠️ (벡터 DB 업체) | ⭐⭐⭐ (로컬 전용) |

**결론**: 개인/소규모 팀이 컨텍스트 주입형 AI를 만들 때는 LLM 위키가 가성비·생산성 면에서 우수하다. 기업 규모 검색 시스템은 RAG가 여전히 필수적이다.

## 시스템 관점의 고려사항

### 1. 비용(Cost)
- **토큰 소모**: 페이지 생성 + 교차 참조 탐색 시 입력·출력 토큰이 많이 발생 [22:53]
- **Claude Pro vs Sonnet Max**: Max 플랜($200/월)이면 무제한 API 사용이라 유리. Pro 플랜은 토큰 압박 가능
- **절감 전략**: 로우 데이터를 **선별적**으로 추가. 핵심 10개 페이지를 먼저 반영 후 추가하면 교차 참조 효율 증가 [16:20]

### 2. 지연(Latency)
- **위키 생성**: 파일 10개 처리에 약 10분 소요 (영상 기준 [18:27])
- **쿼리 응답**: 생성된 위키 페이지를 참조하므로 RAG보다 **빠를 수 있음** (검색 단계 생략, 이미 정리된 페이지만 읽음)
- **트레이드오프**: 사전 정리 시간(위키 생성)이 길지만, 질문 시점에는 정리된 페이지만 읽어 응답 속도 향상

### 3. 신뢰성(Reliability)
- **할루시네이션(Hallucination)**: LLM이 위키 페이지를 생성하므로, 원본에 없는 내용을 "교차 참조"로 포장할 위험 존재
  - **완화책**: 건강 검진 모드로 주기적 검증, 로우 데이터 링크를 위키 페이지에 명시
- **정보 노후화**: AI 업계처럼 빠르게 변하는 도메인은 6개월 전 정보가 무용지물일 수 있음 [23:50]
  - **완화책**: 린트(Lint) 작업으로 모순 탐지, 타임스탬프 기반 우선순위 조정

### 4. 운영(Operations)
- **로깅**: Claude Code가 작업 이력을 `logs/` 폴더에 자동 기록 [10:23]
- **버전 관리**: Obsidian 볼트를 Git으로 관리하면 위키 변경 이력 추적 가능
- **토큰 사용량 추적**: Claude API 대시보드에서 확인 필요 (영상에서 직접 언급 안 됨)
- **캐싱**: 영상에서 명시 안 됨. 향후 Claude의 Prompt Caching 기능 활용 시 반복 페이지 참조 비용 절감 가능

### 트레이드오프 요약
| 선택 | 장점 | 단점 |
|------|------|------|
| **교차 참조 적극 활용** [17:34] | 의외의 연결점 발견, 복리 효과 극대화 | 토큰 소모 증가, 생성 시간 증가 |
| **로우 데이터 전수 반영** | 정보 누락 없음 | 토큰 비용, 노후화 관리 부담 |
| **핵심 10개만 선별 반영** [16:20] | 비용 절감, 집중도 높음 | 정보 커버리지 제한 |

## 코드로 이해하기

영상에 직접 코드가 나오지 않았지만, 프롬프트 패턴을 기반으로 동일 개념을 구현한다면 다음과 같다.

### 예시: LangChain + GPT-4o로 간단한 위키 생성기 (Python)

```python
# 영상의 개념을 LangChain으로 재구성한 예시
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate
from pathlib import Path
import json

llm = ChatOpenAI(model="gpt-4o", temperature=0)

# 1. 로우 데이터 읽기
raw_dir = Path("raw/")
raw_files = list(raw_dir.glob("*.md"))

# 2. 위키 생성 프롬프트 (영상의 claude.md 규칙과 유사)
wiki_prompt = ChatPromptTemplate.from_messages([
    ("system", """당신은 지식 위키 편집자입니다.
    원본 문서를 읽고:
    1. 핵심 개념을 추출해 위키 페이지를 작성하세요.
    2. 다른 문서와 관련성이 있으면 [[페이지명]] 형식으로 교차 참조를 추가하세요.
    3. 기존 위키 페이지가 있으면 업데이트만 하세요."""),
    ("user", "원본: {raw_content}\n기존 위키: {existing_wiki}")
])

# 3. 위키 생성 (실제로는 10개씩 루프, 영상 [18:27])
existing_wiki = {}  # 기존 위키 페이지 딕셔너리

for raw_file in raw_files[:3]:  # 예시로 3개만
    raw_content = raw_file.read_text()
    
    response = llm.invoke(
        wiki_prompt.format_messages(
            raw_content=raw_content,
            existing_wiki=json.dumps(existing_wiki, ensure_ascii=False)
