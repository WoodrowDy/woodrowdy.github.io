# 바로 써먹는 하네스 엔지니어링 6단계 로드맵 — 실전편 파트 1

## TL;DR

클로드 코드로 긴 작업을 안정적으로 이어가려면, (1) 클로드.md를 60줄 이하로 유지하며 실패 시 한 줄씩 추가하고, (2) 사용 중인 MCP/도구만 켜서 컨텍스트를 아끼며, (3) 세션 간 인수인계 문서(progress.md + feature-checklist.md)를 만들어 작업 단위를 40% 이하 컨텍스트 소비로 쪼개는 것이 핵심입니다. [00:41]

---

## 영상의 핵심 주장

- **클로드.md는 "지도"이지 백과사전이 아니다** [03:53]  
  수백 줄짜리 규칙 문서는 AI가 핵심을 파악하지 못하고, 낡은 규칙 무덤으로 전락하며, 토큰만 낭비한다 [02:24].

- **MCP 서버를 많이 연결할수록 인스트럭션 예산이 줄어든다** [06:46]  
  Anthropic이 공식 발표한 문제로, 도구 설명이 컨텍스트를 잠식해 정작 사용자 명령 처리 공간이 사라진다 [06:56].

- **컨텍스트 창이 40% 이하일 때 작업을 마쳐야 이상적이다** [11:16]  
  40%를 초과하면 작업 단위가 너무 크거나 불필요한 정보가 쌓인 것이며, 성능 저하가 시작된다 [11:23].

- **세션 간 인수인계 문서(progress.md + feature-checklist.md)가 필수다** [09:38]  
  Anthropic은 이 두 파일로 "퇴사자 → 신규 입사자" 인계를 자동화하여 Claude.ai 클론 프로젝트를 완성했다 [12:45].

- **작업은 기능 단위로 쪼개고, 하나 끝날 때마다 커밋 → 진행 문서 업데이트 → 새 세션 시작** [12:19]  
  한 번에 모든 기능을 구현하려 하면 컨텍스트가 바닥나서 실패한다 [12:23].

## 이론적 배경

### Harness Engineering의 본질: 상태 관리 + 작업 연속성

하네스 엔지니어링은 **장기 실행 워크플로(Long-Running Workflow)**를 AI 에이전트에 맡길 때, 세션 단절에도 작업이 이어지도록 **상태(state)를 외부화**하는 패턴입니다. 분산 시스템의 **Saga 패턴**이나 **BPMN(Business Process Model and Notation)**과 유사하게, 작업 단위를 명시적으로 정의하고 중간 상태를 기록(checkpoint)합니다.

### 컨텍스트 윈도우 = 제한된 자원

LLM의 컨텍스트 윈도우는 **제한된 메모리**입니다. 불필요한 도구 설명, 낡은 대화 로그로 채우면 **Thrashing**(유효 작업보다 메모리 관리에 더 많은 비용 소비)이 발생합니다. 이는 OS의 페이지 교체 알고리즘과 유사한 문제이며, 영상에서 언급한 "인스트럭션 예산(instruction budget)" [06:51]은 실질적으로 **유효 프롬프트 용량**을 의미합니다.

### Actor Model 관점: 메시지 기반 상태 전이

각 세션을 Actor로 보면, 세션 종료 시 상태를 `progress.md`에 직렬화(serialize)하고, 다음 세션이 이를 복원(deserialize)하는 구조입니다. Actor Model의 핵심인 **"공유 상태 없이 메시지로만 통신"** 원칙을 AI 워크플로에 적용한 사례입니다.

## 기존 솔루션과의 비교

| 접근법 | 상태 관리 방식 | 세션 연속성 | 컨텍스트 비용 |
|--------|--------------|------------|--------------|
| **하네스 엔지니어링** | progress.md + feature-checklist.md로 명시적 저장 | 인수인계 문서 기반 복원 | 40% 이하 유지 목표 [11:16] |
| **LangGraph** | StateGraph의 노드 간 상태 전달 | 체크포인트 저장 가능, 중단 지점부터 재개 | 그래프 정의가 컨텍스트에 포함됨 |
| **Temporal** | Workflow 상태를 이벤트 소싱으로 영구 저장 | 워커 교체 시에도 이벤트 재생으로 복원 | 워크플로 정의는 코드에만 존재, 컨텍스트 격리 |
| **Airflow** | DAG의 task 상태를 DB에 저장 | 재시도 로직 내장, 실패 task부터 재실행 | 메타데이터 오버헤드 높지만 런타임과 분리 |

**영상의 접근법 특징**  
- 도구는 기본 4가지(파일 읽기/쓰기/편집/bash)만 사용 [07:27], 확장 시에만 MCP 추가  
- CLI 우선주의: MCP보다 CLI가 토큰 절약에 유리 [07:43]  
- 상태 문서(progress.md)는 사람이 읽을 수 있는 마크다운 형식 → 디버깅 용이

## 백엔드 시야로 본 트레이드오프

### 강점

1. **결정론적 워크플로 구성**  
   feature-checklist.md의 boolean 플래그는 NestJS의 `@Injectable()` 서비스 상태처럼, 작업 진행도를 명시적으로 추적 가능하게 만듭니다. 실패 시 롤백 지점도 명확합니다.

2. **저비용 상태 저장소**  
   progress.md는 PostgreSQL 같은 외부 DB가 아닌 로컬 파일 시스템을 상태 저장소로 사용합니다. 네트워크 레이턴시 제로, 트랜잭션 오버헤드 제로.

3. **사람-AI 협업 경계 명확화**  
   클로드.md는 60줄 이하로 제한 [04:26] → "AI가 자율 판단할 영역"과 "사람이 명시해야 할 규칙"의 경계를 강제합니다. 백엔드에서 환경변수를 .env에 명시하는 원칙과 유사합니다.

### 약점

1. **분산 환경에서 동기화 문제**  
   progress.md가 로컬 파일이라면, 팀원이 동시에 같은 프로젝트를 다룰 때 충돌 가능성이 있습니다. Git merge conflict로 해결 가능하지만, 실시간 협업에는 부족합니다.

2. **컨텍스트 40% 임계값의 경험적 기준**  
   [11:16]에서 제시한 40% 기준은 "대규모 마이그레이션 프로젝트"에서 나온 것이지만, 과학적 벤치마크는 아닙니다. 작업 복잡도에 따라 가변적일 수 있습니다.

3. **세션 전환 비용**  
   기능 하나마다 커밋 → 진행 문서 업데이트 → 새 세션 시작 [12:28]은 안정성을 높이지만, 짧은 작업에서는 오버헤드가 클 수 있습니다. Temporal의 Activity 단위처럼 자동 체크포인트가 없어 수동 관리 필요합니다.

### 프로덕션 적용 시 고려사항

- **멀티 에이전트 시나리오**: progress.md를 에이전트별로 분리할지, 공유할지 전략 필요  
- **버전 관리**: feature-checklist.md가 Git으로 관리되면, 브랜치별 작업 진행도 추적 가능  
- **모니터링**: 컨텍스트 사용률을 실시간 모니터링할 도구(e.g., Prometheus exporter) 부재
